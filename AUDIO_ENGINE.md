# Audio Engine

## Streaming pipeline

`SAF URI → ParcelFileDescriptor → Rust/Symphonia → Rust/Rubato → Rust 31-band EQ → Rust bounded PCM ring → Rust AAudio NDK FFI`

`FloweryPlayer.kt` owns Android document access, route selection, playback lifecycle, seek/pause requests, and service-facing state. For the AAudio route it requests bounded pump operations through JNI; `native/src/streaming.rs` performs incremental Symphonia decoding, Rubato resampling, EQ and format-level seeking, then transfers decoded frames directly into the Rust ring without creating a Java float array. `native/src/aaudio.rs` owns the AAudio NDK stream, PCM ring buffer, callback, output lifecycle, and ring-write API. The direct USB route retains Kotlin orchestration only where Android USB permission, device/session lifecycle, and libusb transport calls are required. Rust parses and reads direct WAV PCM, applies decoded-PCM gain and signed-24-bit packing, and owns the bounded queue between the decoder producer and USB writer. The C++ native target is retained only for the independent direct-USB libusb transport.

The JNI surface intentionally exposes the incremental decoder and bounded output operations only. The former whole-file `nativeDecode` API and stateless array-based `nativeResample`/`nativeApplyEqualizer` APIs have been removed, along with their Kotlin declarations and convenience wrapper. This prevents a second, state-resetting DSP route from bypassing the persistent streaming resampler and equalizer state.

## Decode and resampling

Symphonia probes the selected document and decodes the default audio track packet by packet. The streaming path retains pending samples rather than assembling the entire decoded track in one PCM array. Mono and stereo are supported by the current output path. The supported filename-extension registry is maintained in `native/src/library.rs` and queried through JNI by the Kotlin SAF scanner. This is a discovery filter only; it does not guarantee that every corresponding codec can be decoded.

Rubato 5 uses a fixed-ratio synchronous FFT resampler. Its instance and filter history persist across chunks. When source and output sample rates match, conversion is bypassed. USB output rates are selected using Android-reported device information where available, then validated by attempting to open AAudio. This is not exhaustive USB Audio Class capability enumeration.

## 31-band ISO equalizer

The band centers are 20, 25, 31.5, 40, 50, 63, 80, 100, 125, 160, 200, 250, 315, 400, 500, 630, 800, 1000, 1250, 1600, 2000, 2500, 3150, 4000, 5000, 6300, 8000, 10000, 12500, 16000 and 20000 Hz. Each band uses a peaking biquad with gain constrained to -12 dB through +12 dB. Filter state is retained per channel and band across chunks. Runtime gain updates replace coefficients without clearing filter history.

Native tests check chunk-boundary continuity and coefficient finiteness. The project maintainer has also confirmed that the equalizer works in device testing. The Settings → Audio → Information Audio page describes the decode/resample/EQ/output path and displays the current playback status; it does not currently expose per-stage timing or live DSP meters.

## Ring buffer and callback

The AAudio ring capacity is selected from the negotiated output rate: at least two seconds of PCM and at least 32,768 frames, rounded up to a power of two. The Kotlin coordinator requests native pump chunks of up to 8,192 frames and starts output after a 1.5-second low-water mark, bounded to three quarters of the ring capacity. The Rust AAudio callback copies available interleaved float frames, applies output gain, clamps samples, converts to the selected PCM output format, fills underruns with silence, and stops after EOF and queue drain. It does not perform file I/O, decoding, resampling, dynamic allocation, or mutex locking. The producer and callback share a bounded frame-indexed ring buffer; flush pauses the stream before resetting queue indices.

AAudio exclusive sharing is requested first; shared mode is attempted if exclusive opening fails. Shared mode may be mixed or resampled by Android.

## Direct USB PCM processing

The direct WAV route uses `native/src/wav_pcm.rs`. Rust duplicates the Android-provided file descriptor, validates the RIFF/WAVE container and PCM format, locates the data chunk, reads bounded frame-aligned blocks, and performs frame-based seeking. Supported direct PCM is stereo integer PCM16, PCM24, or PCM32. At unity gain the source bytes are passed through unchanged; non-unity software gain applies a stateful block-to-block ramp and changes sample data. Kotlin opens the SAF descriptor and manages Android USB permission and the DAC session, but does not parse WAV chunks or process PCM samples.

For decoded direct USB playback, `native/src/streaming.rs` reads Symphonia output and applies the per-DAC gain ramp before packing signed 24-bit little-endian samples. `native/src/usb_pcm.rs` owns the bounded six-block queue shared by the decoder producer and USB writer. Queue capacity, ordering, timeout behavior, clear-on-seek, and close signaling are implemented in Rust. Kotlin retains producer/writer thread lifecycle, pause/seek intent, Android diagnostics, and submission of packed blocks to the libusb session. The queue is bounded by block count; the current producer uses at most 32,768 stereo frames per block.

The retained C++ translation unit remains exclusively responsible for the libusb isochronous transport. No AAudio implementation is moved into or retained in C++.

## Seeking

Seeking flushes the output ring, performs a format-level Symphonia seek, resets decoder and DSP state, reconfigures the resampler, retains decoder preroll where needed to rebuild Rubato history, and discards output before the requested presentation timestamp. Playback paused/playing state is preserved.

## Output volume policy

Speaker, wired AUX/headphones, and Bluetooth use Android's `STREAM_MUSIC` volume. Flowery reads the current system volume when the UI starts and writes slider changes back to that stream; Android remains responsible for device-specific safe-listening limits and any system warning/confirmation UI. Flowery does not impose a fixed 67% ceiling, because safe-volume thresholds and user override behavior are controlled by Android and may vary by device and region.

USB output uses a separate software gain preference keyed to a stable USB VID/PID identity when Android and direct USB identify the same DAC. A newly encountered DAC defaults to 20%; subsequent slider changes are saved per key and loaded into the UI when a single USB DAC is connected. The Android AAudio route applies gain in its float PCM callback, while direct libusb WAV and decoded-PCM routes apply gain before integer PCM is submitted to the DAC. The direct USB transport does not map physical DAC buttons or query hardware volume controls, so software volume remains available without a physical volume control.

## USB DAC discovery and permission

`UsbDacController.kt` enumerates attached USB devices and identifies interfaces declared as USB Audio Class streaming interfaces. The USB icon requests Android USB host permission for a detected USB Audio Class device; when several are attached, Flowery prefers a permission-granted device and attempts compatible candidates in enumeration order. The KT Micro KT-384/32 HIFI reference device is recognized by VID `0x31B2` and PID `0x0111` for diagnostics only; that identity is not required for direct playback. The additional string `LINUX 55` supplied with the device listing is not interpreted as a USB audio capability because its descriptor field is unknown. After permission is granted, Flowery opens the device temporarily and passes the raw descriptor block to the Rust USB Audio Class parser. Rust parses UAC1/UAC2 streaming alternate settings, endpoint direction/type/packet capacity/synchronization, UAC1 PCM formats and advertised rates/ranges, all AudioControl clock-source entities, playback-terminal clock links, and descriptor truncation. Kotlin only adapts the native JSON result for the Android information UI and performs the Android USB control transfers needed to query clock RANGE. UAC2 stereo playback profiles and their endpoint packet multipliers are parsed and validated in Rust; Kotlin holds only the resulting immutable profile model. The report lists streaming alternate settings, isochronous endpoints, UAC protocol, and any statically advertised UAC1 PCM channels, subslot sizes, bit resolutions, and sample rates. `UsbDacPlaybackProfile` additionally identifies stereo UAC2 OUT isochronous alternate settings by interface, alternate number, channel count, PCM subslot/bit resolution, endpoint address, packet capacity, service interval, and synchronization type. `UsbDacController.openExclusivePlaybackSession()` now opens the Android USB file descriptor with native libusb, claims the selected interface, negotiates the UAC2 clock with SET_CUR and verifies it with GET_CUR, then selects the matching alternate setting. `UsbDacSession.writePcm()` accepts packed signed integer little-endian PCM and submits asynchronous libusb isochronous transfers in service-interval-sized packets. The native PCM staging queue retains incomplete service intervals across writes and is bounded to two seconds of PCM. The transport maintains a bounded sliding window of isochronous URBs: each URB carries at most 64 service-interval packets (8 ms at a 125 µs interval). The in-flight window is sized from the endpoint service interval to target approximately 192 ms of queued audio, with a maximum of 24 URBs. A dedicated native event thread owns `libusb_handle_events_timeout_completed()` for the session; the playback worker submits transfers and waits on callback notifications rather than driving the libusb event loop itself. Completion callbacks publish their state atomically and wake the playback worker. This separates event processing from PCM submission and prevents the writer's blocking/back-pressure work from monopolizing event handling. The window is replenished as URBs complete, and a write returns once its PCM has been accepted into the window, so queued audio continues to play while the producer decodes the next block. A write blocks only for back-pressure when the window is full. Because up to the window depth of audio may be queued, the reported direct-USB playback position reflects submitted audio and can lead audible output by up to that look-ahead. `UsbDacSession.drain()` submits any trailing partial service interval as a short final packet and waits for all queued URBs to complete; it is called at natural end of playback so the tail of a track is not truncated. `UsbDacSession.flush()` cancels queued URBs and discards staged PCM; it is called on seek. Closing the session cancels outstanding URBs, waits a bounded time for them to be reaped, and does not free transfer memory that the kernel may still reference. The libusb per-transfer timeout is disabled for isochronous URBs because a timeout cancels queued URBs and breaks the scheduling chain; a progress watchdog instead raises an error if no URB completes for 1.5 seconds while URBs are queued. Failure diagnostics snapshot the number of outstanding URBs and the idle duration before teardown, so the error report does not misleadingly show the already-cleared queue. Direct USB playback uses 32,768-frame decode blocks to amortize JNI and scheduling overhead. The AAudio route uses bounded Rust pump calls (up to 8,192 frames per call) that decode and enqueue PCM entirely on the native side, avoiding a FloatArray round-trip through Kotlin. The direct decoded-PCM path records the audio duration, transport duration, and transport-to-realtime ratio for each write. Transfer diagnostics are captured before freeing the libusb transfer object. For the user-tested KT Micro descriptor, the playback candidates are on interface 2, endpoint `0x04 OUT`, with 16-, 24-, and 32-bit alternate settings. This descriptor-derived profile selection is not a streaming transport and does not establish a supported sample-rate list. UAC2 clock-source sampling-frequency RANGE requests are queried from advertised clock-source entities when the device accepts the standard class/interface request. A failed or unsupported request is reported as unavailable; rates are never guessed from the product label. UAC1 continuous sample-rate ranges are also reported. The connection is closed after inspection. When several USB audio devices are connected, Flowery tries permission-granted candidates in enumeration order and selects the first device that accepts the requested descriptor-derived profile and clock rate.

When the user enables direct USB exclusive mode, `FloweryPlayer` tries connected UAC2 DACs for a descriptor-derived stereo profile matching the source format and sample rate, then selects a dedicated direct path for supported RIFF/WAVE integer PCM files. `WavPcmSource` reads stereo PCM16/24/32 without decoding, resampling, or EQ. It preserves sample bytes at unity gain and applies a short software-volume ramp when the per-DAC gain is below unity. The player requests the source sample rate, opens the native libusb session, claims the descriptor-selected streaming interface, negotiates the linked UAC2 clock with SET_CUR and verifies it with GET_CUR, selects the matching alternate setting, then submits isochronous OUT packets to the descriptor-selected endpoint. Playback is reported active only after the first successful transfer; the USB icon turns blue at that point. Seek, pause and resume are handled by the direct-path worker. Unsupported formats, channel layouts, bit depths, sample rates or failed USB negotiation stop with an explanatory playback error rather than silently falling back to DSP.

When USB exclusive mode is enabled for a supported non-WAV source, `FloweryPlayer` uses Symphonia to decode stereo audio to float PCM, applies the configured DSP, quantizes the result to packed signed 24-bit PCM, and sends it through the same native libusb UAC2 transport. This bypasses Android's audio mixer but is not source-bit-perfect playback. The transport records the selected endpoint's packet capacity, service interval, and synchronization type. On an isochronous transfer failure, the native error includes a failure reason (`transfer_error`, `packet_error`, `submit_failed`, `stalled`, `event_loop_error`, or `packet_exceeds_endpoint_capacity`), the libusb transfer status with its symbolic name (for example `TIMED_OUT`, which is value 2, distinct from `ERROR`, which is value 1), the URB sequence number, the number of URBs queued, and the first failed packet's status and actual/requested lengths where available, together with the endpoint, service interval, and sample rate. These diagnostics identify the failing USB layer; they do not by themselves establish a hardware-verified bit-perfect result.

The direct WAV path uses a per-DAC software volume preference (20% default for a newly seen DAC) so playback remains controllable when the DAC has no physical volume control. Gain is applied with a short block ramp to 16-, 24-, or 32-bit integer PCM. At unity gain, source sample bytes are left unchanged; any non-unity gain intentionally changes the PCM samples and therefore is not bit-perfect. The decoded direct USB path (for example FLAC) is not source-bit-perfect, because its samples are already decoded to float and quantized to 24 bits, so it applies the same per-DAC software gain preference described above (default 20% for a newly seen DAC) together with the 0.25 ducking gain. Gain is applied in the float domain before quantization, is changed linearly across each decoded block to avoid audible steps when the slider moves, and the result is clamped to the range of a 24-bit sample. Flowery does not yet detect hardware-volume capability or map physical volume keys. The normal Symphonia → Rubato → EQ → AAudio path remains unchanged when USB exclusive mode is disabled.

## Decoded direct USB pipeline

The decoded direct USB path uses two threads so that the isochronous transport is never starved while the decoder works. The producer thread (`FloweryUsbDecoder`) reads 32,768-frame float blocks from the native decoder, applies gain, quantizes to packed signed 24-bit little-endian PCM and places each block in a bounded queue of six blocks. The writer thread (the player worker, raised to `THREAD_PRIORITY_AUDIO`) waits until three blocks are queued before the first write, then repeatedly takes a block and passes it to `UsbDacSession.writePcm()`, so decode, gain and quantization time no longer adds to the interval between writes. The producer is the only thread that uses the native decoder handle while it runs and is joined before the handle is closed. Seeks are serviced by the producer: it seeks the decoder, discards queued blocks and increments an epoch counter; the writer flushes the USB transport when it receives the first block of a new epoch, so audio from the previous position is not played. The producer remains idle after reaching the end of the stream so that a seek issued while the final blocks are still queued is honored. A producer failure is reported on the writer thread through the normal playback-error path.

The USB diagnostic log records `USB_PCM_GAIN` (initial gain and queue configuration), `USB_PREBUFFER_READY`, a `queuedBlocks` value on every `USB_WRITE` line, and `USB_PRODUCER_STARVED` whenever the writer waits more than 5 ms for the next decoded block after playback has started. A log without `USB_PRODUCER_STARVED` entries indicates that decoding keeps ahead of the DAC. The reported playback position still reflects submitted audio and can lead audible output by the transport look-ahead.

## Output limitations

The source-bit-preserving direct path is limited to stereo RIFF/WAVE integer PCM16/24/32 on UAC2 DACs that advertise a matching profile and accept the exact sample rate. Decoded formats can use the same direct transport as processed 24-bit PCM, but are not bit-perfect. UAC1, multichannel output, AIFF/DSD passthrough, and floating-point WAV passthrough are not implemented. The sliding-window transport has been exercised only against a simulated libusb layer (byte-exact delivery, window bound, drain, flush, and stall detection) and has not yet been validated across physical DAC models with USB protocol traces or external digital capture. A successful UAC2 clock readback and completed isochronous transfers are necessary runtime checks, but external measurement is still required before making a hardware-verified bit-perfect claim. The normal AAudio path outputs PCM float and can fall back from exclusive to shared mode; it is not bit-perfect. Gapless playback and crossfade are also not implemented.


## Lyrics parsing

LRC parsing runs in Rust through the native JNI boundary. The parser recognizes one- to two-digit minute fields, two-digit seconds, and optional one- to three-digit fractional seconds; it expands multiple timestamps on a line, removes timestamp tokens from the lyric text, and sorts entries chronologically. Kotlin retains only the UI model adapter and current-line presentation lookup. Sidecar document discovery and file access continue to use Android's Storage Access Framework.


## Playlist parsing

CUE, M3U, and PLS parsing runs in Rust through JNI. The native parser produces structured metadata and playlist entries; Kotlin adapts those values to app models. Charset selection and document-tree path resolution remain in Kotlin because they depend on Android/JVM and SAF APIs.


## Playback queue policy

Next, previous, natural-completion, shuffle, and repeat transition decisions are implemented in `native/src/queue.rs` and exposed through JNI. `PlaybackService` retains Android service state and the URI/metadata arrays required by notifications and media sessions, but delegates queue index transitions to Rust. The native transition function returns an explicit stop result or a replay-current result for repeat-one completion; queue index, queue size, repeat mode, shuffle state, and transition policy are owned by a native Rust queue-state handle. Kotlin retains only an adapter for Android service and notification integration.

## Playback orchestration and queue state

`PlaybackCoordinator` is an Android service adapter backed by a native Rust playback lifecycle-state handle; it forwards platform commands to `FloweryPlayer` and defers native handle destruction until the worker exits. `PlaybackService` routes media-session commands through this coordinator. `PlaybackQueueState` is a thin JNI adapter. Rust owns queue selection, repeat mode, shuffle state, and navigation transitions; the Android service retains URI and metadata collections required by platform notifications and media sessions.

## USB Audio Class descriptor parsing

UAC2 stereo playback alternate-setting selection and playback-terminal clock-source resolution are implemented in `native/src/usb_descriptors.rs`. Android retains USB permission and connection ownership, while the native parser validates descriptor boundaries, endpoint direction/type, channel count, PCM subslot/bit resolution, packet capacity, and terminal-to-clock relationships. Kotlin maps the native JSON result into Android USB session parameters. Descriptor parsing alone does not prove that a device accepts a clock rate or that the resulting signal is bit-perfect; the libusb SET_CUR/GET_CUR check remains mandatory.
